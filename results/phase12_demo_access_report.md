### B. Startup Seeding Mechanism (`main.py`)
In `main.py`, the `_seed_demo_doctor_on_startup()` lifecycle hook checks for the existence of `dr.carter@hospital.org` in the database. When `DEMO_MODE=true` (as configured on Render and in development):
- Creates or updates the record using standard `hash_password("demo-doctor-2026")`.
- Sets `email_verified = True` and `verification_status = "APPROVED"`.
- Never prints passwords or tokens to logs.
- Does not create duplicate demo accounts.

### C. Frontend One-Click Interaction (`UnifiedLogin.jsx`)
Clicking **Quick Demo Access (Dr. Julian Carter, MD)** in the login interface triggers `handleQuickDemo()`:
```javascript
const handleQuickDemo = async () => {
  const demoEmail = 'dr.carter@hospital.org'
  const demoPassword = 'demo-doctor-2026'
  setEmail(demoEmail)
  setPassword(demoPassword)
  await performLogin(demoEmail, demoPassword, false)
}
```
`performLogin` dispatches a standard `POST /auth/login` payload:
```json
{
  "email": "dr.carter@hospital.org",
  "password": "demo-doctor-2026",
  "remember_me": false
}
```

## 4. Security & Compliance Guarantee
1. **No Frontend Hardcoded Bypass:** Authentication is not mocked; token validation and session cookies are generated by FastAPI.
2. **Standard Hash Verification:** Uses identical verification paths (`verify_password`) as standard registered physicians.
3. **No Credential Exposure:** Neither the database connection strings nor demo doctor secret keys are stored in client-side bundles.
